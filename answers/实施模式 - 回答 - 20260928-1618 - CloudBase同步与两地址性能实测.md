## 6. 关键实测数据

### 6.1 性能对比（`data/recipes.json`，735 KB，各测 3 次）

| | GitHub Pages | CloudBase |
|---|---|---|
| 传输大小 | 252 KB（**已 gzip**） | 735 KB（**未压缩**） |
| 耗时 | 1.31 / 1.55 / 1.68 s | 0.35 / 0.40 / 0.43 s |

**关键推论**：CloudBase 传输的数据量是 GitHub 的 **3 倍**，却**快约 4 倍**。
→ **瓶颈是国际链路，不是文件体积。**

**由此排除一条原以为可行的优化路线**：曾考虑「压缩 `recipes.json` 以加速」，
但实测 GitHub Pages **已自动 gzip**（735 KB → 252 KB），收益已被吃满；
且 CloudBase 不压缩反而更快，说明压缩不是矛盾主因。**换托管才是有效解法。**

### 6.2 警告页机制

CloudBase 默认测试域名的「页面访问提示」**只在首次访问出现**：
点击「确定访问」后，**同一浏览器再次访问直接进入应用**（已实测两次访问验证）。
即每个**新访客**需点一次，熟悉后不再麻烦。

### 6.3 微信兼容风险（本轮最重要的发现）

本项目的核心分享场景是**微信内发链接**。而：

- 开发者社区有记录：`github.io` 域名**在 QQ 与微信中被屏蔽**过；
- GitHub 曾对**中国大陆 IP 返回 403**（登录页面同样被拦）。

→ GitHub Pages 存在「**链接发出去、对方打不开**」的实质风险。
CloudBase 是腾讯自有域名，微信生态内兼容性更稳。

## 7. 为什么这样改

1. **为什么推荐 CloudBase 而不是速度更"干净"的 GitHub Pages**：
   速度上 CloudBase 快 4 倍；更关键的是**微信内被屏蔽风险**——
   分享场景下"对方打不开"是致命的，而"首次多点一次"只是轻微不便。
   两害相权，选 CloudBase。
2. **为什么保留 GitHub Pages 不删**：两处都可用，且 GitHub Pages **无警告页**。
   若将来微信兼容性改善、或用于非微信场景，它仍是干净选择。
   文档给出对照表而非单一结论，让读者可自行取舍。
3. **为什么把"实测数据"写进文档而非只给结论**：性能结论**依赖网络环境**，
   本机数据不代表用户手机网络。写出测法与数值，后来者可复现、可证伪。
4. **为什么标注"未经真实微信验证"**：本机无法模拟真实微信客户端，
   屏蔽风险来自**社区记录**而非本地实测，属**间接证据**，必须如实标注。

### 测试审计

第 3–6 项**直接证明**「CloudBase 已与 GitHub Pages 对齐」这一验收标准——
用两边线上实际响应比对，而非依据"部署命令返回成功"作推断
（部署成功 ≠ 线上生效，CDN 缓存等都可能造成偏差，故以线上响应为准）。

第 7 项证明的是「警告页不是次次出现」，**不等于**「体验无感」——
新访客仍会遇到一次，该事实已写入文档。

第 8 项性能数据的**适用边界**：仅代表**本机网络环境**，
不代表用户手机移动网络；已在文档中标注。

## 11. 后续建议

1. **请你在微信里实测一次**：分别发两个地址给自己，看哪个能正常打开、哪个快。
   这是唯一能确认 U1 的方式，也直接决定以后该发哪个链接。
2. 若确定长期用 CloudBase，可考虑**开启 gzip** 或**绑定自定义域名**
   （后者需备案，属较大动作，非必需）。
3. **`skipped`**：未尝试压缩 `recipes.json`——实测证明该项对 GitHub 收益有限
   （已自动 gzip），对 CloudBase 也非瓶颈；若将来换用其他托管可重新评估。
4. 小程序端「转发给朋友」仍不可用（需认证）——属已决策终态，非缺陷。
