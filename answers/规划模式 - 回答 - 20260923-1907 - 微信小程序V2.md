### 4.3 依赖边界分析（决定「能复用多少」的关键）

按「能否脱离 DOM / localStorage / fetch」把现有代码分成三层：

| 层 | 内容 | 小程序可复用性 | 证据 |
|---|---|---|---|
| **A 纯计算层** | 整个 `nutrition.js` | ✅ **可直接复用**，一行不改 | 全文无宿主 API |
| **B 纯业务逻辑层** | `menuPlan` / `sampleDistinct` / `sameMenu` / `pickMenu` / `isBlocked` / `rebuildAvailable` / `parseKeywordInput` / `dedupeKeywords` / `effectiveDiners` / `menuPlan` 相关常量 | ✅ **可复用**，但它嵌在 `app.js` 内部、与渲染交织，无法在不改 `app.js` 的前提下被外部引用 | `app.js:120-153`、`309-395` |
| **C 宿主绑定层** | DOM 渲染、事件、`localStorage`、`fetch`、`file://` 检测 | ❌ **必须重写** | `app.js:89-118`、520-1307、1336-1344 |

**由此得到三条结论：**

1. **`nutrition.js` 不需要修改，也不需要重写** → H14 成立的一半。
2. **B 层无法在不修改 `app.js` 的前提下被共享**（它是文件内私有函数，没有导出）→ 若不碰 Web，小程序端**必须有一份等价实现**。
3. **C 层本来就必须重写**（小程序没有 DOM）→ 与 H14 无关。

**因此：「必须修改现有 Web 代码」不存在。** 唯一代价是 B 层会出现一份等价实现，本规划用「构建期一致性断言 + 源头注释锚点」把这份代价控制在可验证范围内（见第 8 节）。

## 5. V2 目标与范围

### 5.1 目标（本规划的回答）

> 把 V1 已经验证过的**核心能力**，以**最小、稳定、易维护、与 Web 版关系清楚**的方式做成微信小程序，让用户在微信里能真正方便地打开并使用。

### 5.2 V2 第一版包含（in scope）

1. 打开小程序即见**一荤一素**（默认），可切 2/4/6/8 道，荤素始终 1:1
2. **换一组**，同桌不重复，池子不足明确报错并禁用换组
3. **屏蔽关键词**（含增删清空）
4. **菜谱详情**：菜名 / 分类 / 难度 / 简介 / 食材 / 做法 / 小贴士 / 来源
5. **健康与营养**：默认关闭；开启后含家庭成员（最多 8 位、每人独立每日能量参考、自动估算或自己设定）、本次用餐人数、每天通常吃几餐（只记录）、主食准备量、这桌菜估算（合计 + 数学平均）、单道菜营养估算（含覆盖率）、按成员分别的 BMI / 基础代谢 / 宏量参考
6. 全部设置存本机（`wx.setStorageSync`），不上传、不需账号
7. 交付形态：**开发版 / 测试版**，用户本人在微信里真实体验

### 5.3 V2 第一版不做（全部留给 V3）

手机维护菜谱 · 增删改菜谱 · 收藏 · 历史菜单 · 近期不重复 · 偏好 · AI 推荐 · 食材库存 ·
购物清单 · 社交功能 · 评论 · 多用户账号 · 家庭成员云端账号 · 多设备同步 · 完整后台管理系统 ·
正式发布 / 搜索上线 / 备案 / 商业化 / 后台运营

**也不为 V3 提前搭后端架构。**

| 4. 是否需要额外框架 | ❌ **不需要** | 同上 |

## 7. 微信小程序目录 / 文件建议

### 7.1 页面划分（3 个主页面 + 1 个子页面）

| 页面 | 路径 | 内容 | 对应 Web 端 |
|---|---|---|---|
| 首页 | `pages/index/index` | 荤素卡片列表、换一组、提示条；健康与营养开启后追加主食区与「这桌菜估算」 | `index.html` 的 `.menu` + `.actions` + `#staple-panel` + `#nutrition-panel` |
| 详情 | `pages/detail/detail` | 菜名/分类/难度/简介/食材/做法/小贴士/来源；开启后追加单道菜营养估算 | `#detail` 面板（`app.js:1028-1058`） |
| 设置 | `pages/settings/settings` | 每餐数量 2/4/6/8、屏蔽关键词、健康与营养开关 | `#settings` 面板前半段 |
| 成员 | `pages/settings/member` | 成员列表 + 新增/编辑表单 + 删除二次确认 + 健康参考 | `#settings` 的 `#hn-sections` + `#member` 面板 |

**为什么成员单独成页**：Web 端用的是 Sheet 弹层，小程序里表单 + 列表 + 健康参考塞进一张设置页会过长。拆成子页面更接近小程序的原生交互习惯，且不需要 `Sheet` 组件库。

### 7.2 页面与模块职责边界（关键设计）

- `lib/menu.js`：**只放纯函数，不出现任何 `wx.` 调用**。这样它能被 Node 直接 `require` 做自动化断言（见第 14 节）。它负责随机、屏蔽、去重、设置归一化。
- `lib/store.js`：**唯一出现 `wx.getStorageSync` / `wx.setStorageSync` 的地方**。
- 页面 `.js`：只做「取数据 → 组装视图模型 → `setData` → 处理事件」，不写业务算法。
- WXML 里不做逻辑判断，`roleLabel` / 卡片摘要 / kcal 文案等**在 JS 里预先算成字符串**（小程序 WXML 不支持函数调用）。

### 7.3 存储设计

| 项 | 值 |
|---|---|
| API | `wx.setStorageSync` / `wx.getStorageSync` |

## 8. Web 与小程序如何复用数据和业务逻辑

### 8.1 复用策略总表

| 资产 | 策略 | 是否改 Web |
|---|---|---|
| `data/recipes.json` | 构建生成 `miniprogram/data/recipes.js`，**全量字段原样搬运** | ❌ |
| `data/foods.json` | 构建生成 `miniprogram/data/foods.js`，原样搬运 | ❌ |
| `nutrition.js`（A 层） | 构建生成 `miniprogram/lib/nutrition.js`，**机械转换 ESM → CommonJS** | ❌ |
| B 层业务逻辑（随机 / 屏蔽 / 归一化） | `miniprogram/lib/menu.js` 等价迁移，函数名与语义保持一致，头部标注来源锚点 | ❌ |
| C 层（渲染 / 事件 / 存储 / 请求） | 小程序端全量重写（WXML + 事件 + `wx` API） | ❌ |
| `styles.css` | **不复用**。小程序用 WXSS，选择器与盒模型差异大；只继承配色变量与卡片视觉语言 | ❌ |

### 8.2 为什么 `nutrition.js` 要转 CommonJS

小程序原生支持的模块格式以 CommonJS（`require` / `module.exports`）**无争议**；ESM (`import`/`export`) 的第三方说法互相矛盾（检索结果中同时存在「小程序完全支持 ES6 语法」与「原生小程序不支持 import/export」两种相反结论）。

**本规划不赌这个不确定性**，统一转成 CommonJS。转换规则是机械且可断言的：

```text
^export function NAME   →  function NAME          （收集 NAME 进导出表）
^export const NAME      →  const NAME             （收集 NAME 进导出表）
文件末尾追加            →  module.exports = { ...收集到的所有 NAME }
```

`nutrition.js` 中没有 `export default`、没有聚合 `export {}`、没有重导出，因此上述三条规则**足以覆盖全部导出**。构建脚本必须断言「源文件 export 名集合 == 转换后导出键集合」，集合不等则构建失败。

### 8.3 为什么 B 层是「等价迁移」而不是「共享引用」

B 层函数（`pickMenu` 等）是 `app.js` 的**文件内私有函数**，既没有 `export`，也依赖同文件的 `settings` / `state` 模块级变量。要共享必须改 `app.js` 的结构 —— 这在 H14 下不被允许，且属于「为了架构漂亮而重构」，与需求五第 6 条相悖。

**代价与缓解**：

| 代价 | 缓解措施 |
|---|---|
| 随机/屏蔽逻辑有两份 | 1) `lib/menu.js` 头部写死来源锚点：`// 移植自 app.js:338-395 pickMenu（基线 deabc45），两处改动必须同步`；2) 第 14 节的断言直接对着同一份菜谱数据跑，行为不一致会立刻暴露；3) 在 `specs.md` 6.x 中把这两个函数补进「跨实现必须一致」清单 |
| 将来改一处忘另一处 | 断言脚本 `tools/check-miniprogram.mjs` 中增加「随机算法不变量」检查（荤素 1:1、不重复、池子不足报错），这些不变量与实现无关，两边都该满足 |

### 8.4 菜谱数据进入小程序的方案取舍

| 方案 | 可行性 | 结论 |
|---|---|---|
| **A. 构建生成 `recipes.js`（对象字面量模块）** | ✅ 无争议可行 | **采用** |
| B. `require('./data/recipes.json')` | ⚠️ 社区多用，但官方文档未明确背书 | 备选，实施时若 A 有性能问题再实测 |
| C. `wx.getFileSystemManager().readFileSync()` 读代码包内文件 | ⚠️ 存在该能力的资料，但路径语义需实测 | 备选，不作为第一方案 |
| D. 放云存储 / 静态托管，启动时 `wx.request` | ❌ | 违反 H10 离线可用；且需配置合法域名 |

**方案 A 的字段策略：全量搬运，不裁剪。** 理由：裁剪字段会造成「小程序端缺字段 → 详情页渲染不出来」，而全量搬运的体积代价是可接受的（见 8.6）。唯一例外见下条。

### 8.5 防止数据分叉的机制（硬性）

`tools/build-miniprogram.mjs` 在生成后**必须断言**，任一不成立即构建失败：

| 断言 | 期望值 | 来源 |
|---|---|---|
| 菜谱总数 | `370` | `specs.md` 6.2 |
| `menuRole = protein` 数量 | `188` | `specs.md` 6.2 |
| `menuRole = vegetable` 数量 | `40` | `specs.md` 6.2 |
| 食物条目数 | `123` | `specs.md` 6.3 |
| `staple: true` 条目数 | `10` | `specs.md` 6.3 |
| 生成物条目数 == 源 JSON 条目数 | 逐条相等 | 本次构建 |
| `nutrition.js` 导出名集合相等 | 集合相同 | 本次转换 |

> 这些数字若因数据重建而变化，**必须同步更新 `specs.md` 与断言**，而不是删掉断言。断言是「防分叉」这件事唯一可自动验证的形式。

## 9. CloudBase 评估结论

### 9.1 用户问的是

> 现有环境 `what-should-we-eat-d0cym0b8ea64c` 对 V2 微信小程序开发到底能不能直接复用，以及最小接入方式是什么。

### 9.2 技术调查结论

| 项 | 结论 |
|---|---|
| 现有环境当前状态 | 只开了**静态网站托管**，无数据库、无云函数（`README.md:489` 实测记录） |
| 小程序能否用这个环境 | **技术上可以**：腾讯云侧创建的环境可在微信开发者工具「云开发控制台 → 设置 → 环境设置 → 管理我的环境 → 使用已有腾讯云环境」导入 |
| 前提条件 | **小程序绑定的腾讯云账号，必须与创建该环境的腾讯云账号一致**。不一致时需要先去腾讯云账号中心把小程序关联到该账号 |
| 是否需要付费 | 云开发按套餐/用量计费。**本轮不订购、不购买任何资源**（需求六硬性要求） |
| V2 第一版是否需要它 | **不需要** |

### 9.3 结论

```text
CloudBase：不需要（V2 第一版）
```

理由：

1. V2 第一版**没有任何一处需要服务端**：菜谱随包分发，设置存本机，无账号、无同步、无共享（H9、H12）。
2. 接入云开发会引入「小程序 AppID ↔ 腾讯云账号」绑定核对、环境导入、潜在计费面 —— 全部是无收益的复杂度。
3. 需求六明确规定：「不要为了『既然有 CloudBase 就必须用数据库』而增加后端」。

**V3 的预判（仅供参考，本轮不做）**：如果 V3 要做「手机维护菜谱 / 收藏 / 历史 / 多设备同步」，**云端是必需的**，届时这个环境（或同账号下的新环境）大概率可复用；但届时要先确认账号绑定关系，并重新评估计费。**这一条不影响本轮任何决策，也不构成任何提前搭架构的理由。**
