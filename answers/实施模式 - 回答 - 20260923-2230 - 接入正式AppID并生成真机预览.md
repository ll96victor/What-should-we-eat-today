## 6. 为什么这样做

1. **为什么接管用户已登录的 Chrome 而不是让用户复制 AppID**：
   用户明确要求「不要让我自己查后台菜单、不要让我自己复制 AppID」。
   本机已部署 Chrome 接管能力，可直接复用其现有登录态，
   无需重新登录、不触发「正被自动化控制」横幅、不产生额外的扫码或验证码。
2. **为什么只在页面上「读」**：用户明确要求只读取 AppID，
   不得读取或保存 AppSecret、密码、验证码。本轮全程**未点击任何保存/提交按钮**，
   仅执行了导航与文本读取。
3. **为什么删掉 README 里「选测试号即可」的旧说明**：上一轮实测证明测试号
   `touristappid` 无法生成手机预览（服务端拒绝，`code 10`），旧说明会误导用户。
   本轮已改为反映真实能力边界。

### 9.5 本轮发现并修正的测试缺陷（重要）

**缺陷 1：时序问题导致连锁失败。**
原脚本在 `mp.navigateBack()` 之后立即取样 `.entry`，
但页面返回动画尚未完成，`currentPage()` 仍返回详情页，导致第 9–21 项连锁失败。
→ 已加入 `waitForPage()` 轮询（最长 10 秒）与 `ensureHome()` 兜底。

**缺陷 2：第 22 项存在假通过。**
「测试后设置已还原」在设置页根本没进去、没有任何设置被改动时，
会因默认值恰为 `keywords=[]` / `每餐=2 道` 而**误判为通过**——
这是典型的静默失效断言。
→ 已引入 `settingsActuallyChanged` 标志，未真实执行时该断言判为**失败**并说明原因。

修正后重跑，22 项全过且每项均有实测值支撑。
