## 4. 关键发现：成员类型与预期不符

复核后台「成员管理」页，实际状态：

| 区块 | 人数 | 微信官方定义 |
|---|---|---|
| **项目成员** | **2 人** | "参与小程序开发、运营的成员，**可登陆小程序管理后台**" |
| **体验成员** | **0 人** | "参与小程序内测体验的成员，**可打开体验版小程序**" |

即：添加时落在了**项目成员**区块。用户随后尝试在「添加体验成员」里补加同一微信号，
微信提示：

> **"已经是项目的成员了，无需重复添加。"**

用户已确认这 2 位是亲友、接受其持有后台权限，**故本轮不执行任何成员删除**。

### 该反馈的含义（**尚未验证**）

微信的拦截提示**暗示**项目成员可能本就能打开体验版（否则无需以"已是成员"为由阻止添加）。
但这**只是推断**——官方权限表把「体验者权限」列为独立一项，二者关系无权威文档明确说明。

**因此本文件与 README 均不将该推断记为事实**，仍如实记录"体验成员 0 人"，
待用户真机扫码后回填。这是对本轮之前"未经真机验证不下结论"承诺的延续。

## 7. 修正的那处表述（本轮主要文档价值）

README 原「当前状态」表格有一行：

```text
| 对方点开能否打开 | ⏸ 认证后可测（体验版下对方还需是体验成员） |
```

**这句话把两件独立的事混为一谈**：

| 事情 | 受什么约束 |
|---|---|
| **「转发给朋友」能不能点** | **账号级**能力，卡在微信认证 |
| **别人能不能打开你的小程序** | **成员权限**，与认证**无关**，走体验版即可 |

按原表述，读者会以为"对方要打开小程序也得先做认证"——这是错的，会误导后续维护
（甚至可能误导用户去付费认证）。已拆分为两行并补充说明。
