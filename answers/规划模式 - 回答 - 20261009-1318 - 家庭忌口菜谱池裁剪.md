## 3. 需求理解与硬约束继承

### 3.1 真实需求

**需求 A（v1，裁剪）**：用户全家有共同饮食禁忌（海鲜、动物内脏等）。随机菜单出的菜很多不能吃，靠"多随机几次"不划算。要求：**菜谱池本身全部是全家能吃的菜**，全局生效、家人零配置。用户已明确授权修改 `specs.md` 和"重构"。

**需求 B（v2 追加，加菜）**：用户还想把自己爱吃、但库里没有的菜加进来（点名 5 道），并预告后续会持续加菜、可能引入其他菜谱来源。因此本轮要交付的不只是"加 5 道菜"，而是**一个可复用的加菜入口**：以后往目录里放一个 md 文件、重跑构建即可加菜，不必每次改构建脚本。

**需求 B 的范围收敛（用户第三轮澄清后确定）**：库里已存在的菜**忽略不加**；本轮**不写**具体菜谱正文（用户将在另一新对话让 AI 搜索/生成后自行填入）；本轮**不做**联网抓取外部菜谱站。

### 3.2 用户已确认的排除/保留边界（硬性，逐条继承）

**排除（食材含有即排除）**：
- 海鲜类：鱼（含金枪鱼/鳗鱼/鳝鱼/桂鱼/鲈鱼等一切鱼）、虾（含虾米/虾皮/海米/虾干）、蟹（真蟹肉/蟹黄；**蟹味菇除外**）、贝/螺/蛏/蛤/鲍/生蚝/海参/海胆/鱿鱼/章鱼/墨鱼/龙虾/田螺、鱼丸/鱼豆腐/蟹柳/咸鱼/虾酱/鱼露等海鲜制品
- 内脏类：肝（猪/鸡/鸭/鹅）、腰子、大肠/肥肠/小肠/猪肠、肚（猪肚/牛肚/毛肚）/百叶/黄喉、胗/肫（鸡胗/鸭胗）、心（猪心/鸡心/鸭心）、脑（脑花/猪脑）、鸡杂/鸭杂等

**保留（硬性）**：

- 仅用**蚝油**调味的菜（蚝油生菜、蚝油三鲜菇、糖醋里脊、辣椒炒肉等约 33 道）——用户原话"蚝油可以吃一点点"；**生蚝本身仍排除**（清蒸生蚝）

## 6. 最小改动方案

**核心思路：排除与新增都发生在构建期（build-recipes.mjs），运行时逻辑一行不改。** 排除以"人工复核后的排除名单"落地，不在运行时做任何关键词过滤；新增以"本地 md 源料目录"落地，不在运行时做任何菜谱维护 UI。运行时逻辑（app.js、menu.js、settings.js、isBlocked、blockedKeywords、check C 组断言）**零修改**。

五层机制（1-3 为需求 A 裁剪，4 为需求 B 加菜，**5 是 v4 新增、为 1-4 的共同基础**，实施顺序上 5 最先）：

> **v4 对机制 1-3 的修正**：下文出现的 `EXCLUDE_CATEGORIES`、`EXCLUDE_TABLE`、`NEW_DISH_ALERT` 三个名字沿用 v2 写法，但**它们的词表内容不再硬编码在 `build-recipes.mjs` 里，而是从 `data/dietary-rules.json` 读取**（见机制 5.3「单一事实源」）。具体是"脚本内保留常量名但值由文件填充"还是"直接以文件结构驱动、不保留常量名"，由新规划 Agent 决定；硬约束只有一条：**构建脚本内不得出现忌口词字面量**。

1. **`EXCLUDE_CATEGORIES = ['aquatic']`**：上游"水产"目录整体不进数据集（结构性防线：未来上游同步新增的水产菜自动被挡）。执行时需审计确认当前 aquatic 类下没有可吃的非海鲜菜（若有，改为逐菜进 EXCLUDE_TABLE 并报告）。

   **4.5 同名去重改为「来源优先」（L371-384，必改）**

   现有逻辑按 `ingredients.length + steps.length` 打分保留更全者。引入自定义源后**必须改为自定义无条件优先**，否则用户自家做法可能被上游版本静默吃掉（例如日后写一道自定义「香干芹菜炒肉」素版，却因上游版食材条数更多而被丢弃）。

   **5.3 硬性设计要求（新规划必须满足）**

   - **单一事实源**：`build-recipes.mjs` 内**不得再出现任何忌口词的字面量**；机制 1/2/3/4.6 全部从本文件读取。验收方式：`grep` 构建脚本确认无硬编码忌口词（`_template.md`/文档/注释除外）。
   - **fail-closed 读取**：文件缺失、JSON 解析失败、缺必需键、值为空数组 → **构建立即失败**并打印具体原因（中文、指明哪个键）。**绝不允许"读不到规则就当作无忌口继续构建"**——那会让全家忌口静默失效，比构建失败严重得多。
   - **用户改坏要能看懂**：错误信息必须是非技术用户能读懂的中文（例如「`排除食材.海鲜` 不是数组，请检查是否漏了引号或逗号」），不是 stack trace。
   - **`强制保留的菜` 优先级最高**：命中"强制保留"的菜，即使食材字面命中排除词也**必须保留**（这是蚝油类约 33 道菜的保命机制）。构建时校验：强制保留清单里每个菜名必须在数据集中存在，不存在 → 构建失败（防止上游改名导致保护静默失效）。
   - **`字面例外` 必须带理由**：值是字符串说明而非布尔，让后来人知道为什么例外（防止"看着像 bug 就删掉"）。
   - **入库**：本文件是**源料不是产物**，必须提交入库（`.gitignore` 不排除 `data/`，已核查，见 §2 v2 核查）。符合用户全局偏好「`.md`/源料文档必须入库」。
   - **`_说明`/`_改法` 字段是给用户的行内文档**：构建脚本读文件时忽略 `_` 前缀键。这样规则文件自带使用说明，用户不必翻 README 也知道怎么改。

   **5.4 与本文档 §3.2 的关系（防两份规则漂移）**

   §3.2 是**用户确认过程的记录**（含原话、轮次、个案由来），`data/dietary-rules.json` 是**可执行的事实源**。两者不是重复：
   - 规则文件落地后，§3.2 顶部须加一行指引：「**可执行版本见 `data/dietary-rules.json`；本节保留为用户确认过程的历史记录**」
   - 日后改忌口：**只改规则文件**，§3.2 不再同步（它是历史快照，按 CLAUDE.md「文档不得与代码的真实态漂移」原则，历史确认记录不做回填，避免"改一处要改两处"）
   - `specs.md` 的新增规格小节应**指向规则文件**而非复制词表（同样为避免漂移）

   **5.5 新规划 Agent 需要决定的开放问题**
   - 文件名与格式：`data/dietary-rules.json` vs `.md` vs 其他位置（本文档作者倾向 JSON：构建脚本可直接 `JSON.parse`，无需写 md 解析器；md 虽更易读但要额外解析代码，反而增加出错面）
   - 是否需要配套的"规则自检"命令（例如 `node tools/check-dietary-rules.mjs`，让用户改完能先验证再构建）
   - `data/foods.json`（营养表）是否也该有类似的独立说明文件——本轮不建议扩大范围

配套：`stats`/`updatedAt` 随构建自动更新；**数据 schema 零变更**（不新增/删除/改名任何字段，仅 `license` 字符串值与自定义菜的 `id`/`sourceName`/`sourceUrl` 取值发生变化，这三个字段本就存在）；因此 `check-miniprogram.mjs` 与两端运行时代码无需为 schema 改动。唯一必须同步的硬编码是 `build-miniprogram.mjs` L33-35 的三个数量断言（已确证存在，见 §2 v2 核查）。

**为什么不做其他方案**（已比较）：

*需求 A（裁剪）：*
- 纯屏蔽词（零改动）：无法表达"蚝油保留但虾米排除、鱼香肉丝保留"；且设置不跨设备同步，全家每台设备都要配置——被用户的"全家零配置"需求否决。
- 预设包一键导入：同样有跨设备配置负担和关键词精度问题，仅解决输入便利。
- 运行时标签系统：精度可达标，但要动数据 schema + 两端运行时 + 断言 + 设置 UI，且家人仍需每台设备开开关——比构建期排除多一整层运行时复杂度，违反"不提前搭架构"设计原则。
- 手工删除 recipes.json 条目：上游 `--refresh` 一跑就恢复，且违反"数据只能由构建脚本生成"的既有约束。

*需求 B（加菜，v2 新增比较）：*
- **在 `build-recipes.mjs` 里硬编码 5 道菜的 JS 对象**：一次性可行，但用户已预告"等会还要加、可能引入其他菜谱来源"，每加一道都要改脚本并冒改坏构建的风险；且菜谱正文（长文本步骤）塞进 JS 常量里可读性极差、diff 难审。否决。
- **手工往 `data/recipes.json` 追加条目**：违反 §3.3-2 数据唯一事实源；`--refresh` 或任何一次重建都会把手工条目冲掉，属于典型的"改产物不改源料"，必然漂移。否决。
- **本地 md 源料目录（选定方案）**：复用现有解析器（零新增解析代码）、源料可读可 diff 可入库、加菜成本 = 放一个文件 + 重跑构建、天然为"日后引入其他菜谱来源"留好入口（整理成同格式 md 即可）。且与项目既有"人工复核修正表"（`ROLE_OVERRIDE`）的设计哲学一致：**人工判断落在可读的源料/表格里，不落在运行时逻辑里**。
- **运行时"我家菜谱"功能（手机端增删）**：这是 specs §11 的 V3 方向，需要 UI + 存储 + 跨设备同步，且家人每台设备各自维护——与用户"全家零配置"需求相悖，用户第三轮也已明确"既然库里有那就忽略"（不追求运行时偏好能力）。本轮不做。
- **联网抓取第三方菜谱站直接入库**：版权风险实质存在（第三方站点内容非 Unlicense），且抓取质量/格式/反爬均不可控。用户已明确本轮不做，留待独立任务并先做许可筛选。

| | 路线 A：搜**具体几道菜的做法** | 路线 B：引入**另一个整库菜谱数据源** |
|---|---|---|
| 用户表述契合度 | 契合"我想加一点菜"（点名 5 道） | 契合"其他的菜谱来源"字面 |

## 11. 回滚思路

- 单 commit 交付：`git revert` 即恢复代码+数据+文档；`history/` 另有文件级备份（T2）
- 线上：revert 后重新 push（Pages 自动）+ 重跑 CloudBase 部署
- 小程序：旧体验版本未被覆盖前天然保留旧数据；上传新版后如需回退，用旧代码重新上传即可
- **（v2）自定义菜源的独立回滚**：若只想撤掉某道/全部自定义菜而保留裁剪成果——删除或改名对应 md 文件（或整个 `data/custom-dishes/` 目录），重跑 `build-recipes.mjs` + `build-miniprogram.mjs` 即可，**无需改任何代码**（A15 已验证目录缺失时构建正常）。这条要写进 README，让用户自己就能撤。
- **（v2）分层回滚顺序建议**：先试"删 md 重建"（最小代价）→ 不行再 `git revert` 整个 commit → 最后才考虑从 `history/` 手工恢复文件
- **（v4）忌口规则文件的回滚**：`data/dietary-rules.json` 入库 ⇒ 用户改坏了可直接 `git checkout -- data/dietary-rules.json` 恢复到上次提交态，或从 `history/` 取备份。**但用户是非技术背景，不应要求他跑 git 命令**——规划时应考虑：① 错误信息足够清楚，让他知道改错了哪一行 ② 可选的自检命令（§12.3 第 13 项）在构建前就拦住 ③ README 写明"改坏了怎么办"（最简答案：找 AI 说"我把忌口文件改坏了，帮我恢复"）
- **（v4）注意 fail-closed 与回滚的交互**：规则文件损坏时构建会失败（这是设计意图），意味着**无法用"重跑构建"来恢复**——必须先把文件本身修好或还原。规划时不要把"重跑构建"当成规则文件的回滚手段。
