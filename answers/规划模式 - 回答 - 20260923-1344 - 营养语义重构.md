
## 4. 代码现状与相关文件（事实，含行号）

> 以下全部为实测，非推测。

### 4.1 每日能量在哪里定义、计算、展示

| 环节 | 位置 | 事实 |
|---|---|---|
| 计算 | `nutrition.js:274-305` `healthMetrics()` | `bmr`（Mifflin-St Jeor）、`tdee = bmr × 活动系数`，以及按 `tdee` 推导的 `carbsLow/High`、`fatLow/High`、`proteinG` |
| 展示 | `app.js:724-731` `renderMemberHealth()` | 成员卡片四格：`BMI` / `基础代谢`(bmr) / `维持能量`(tdee) / `蛋白质` |
| 脚注 | `app.js:730-731` | `碳水 x–y g　·　脂肪 x–y g　·　每天` |

**关键结论：项目当前不存在「每日能量参考」这一概念。**

存在的只是一个由公式即时算出的「**维持能量**」（TDEE），旁边挂着「**每天**」两个字。用户看到「维持能量 2362 kcal · 每天」，非常容易读成「我每天应该吃 2362 kcal」——这正是要求 1 要修正的误导点。

同时它**不持久化、不可覆盖**：每次渲染现算。

### 4.2 本餐营养在哪里计算、展示

| 环节 | 位置 | 事实 |
|---|---|---|
| 计算 | `nutrition.js:220-242` `summarizeMeal()` | `total`（合计）、`perPerson = total ÷ people` |
| 面板 | `app.js:566-613` `renderNutrition()` | 两列：`整顿饭` ｜ `N 人平均` |
| 面板脚注 | `app.js:609-612` | `按菜谱所写用量估算：X 道菜 + 米饭 750g` / `X / Y 道菜有可用营养数据` / `菜谱未按人数折算，实际按你下锅的量同比变化` |
| 首页卡片 | `app.js:470-473` `cardHtml()` | `约 xxx kcal`（**裸数字，无任何范围前缀**） |
| 详情页 | `app.js:421-449` `recipeNutritionHtml()` | `按菜谱所写用量（整锅）` |

### 4.3 家庭成员与每日能量之间是什么关系

**没有任何持久化关系。** 每位成员的参考值只在渲染时由 `healthMetrics(member)` 即时计算，公式**只依赖该成员自己的资料**，人数不参与（`specs.md:139-141` 已规定）。

成员与「今天几个人吃」也是分离的：`members` 描述「家里有谁」，`currentMealHouseholdSize` 描述「今天来几个」（`specs.md:86-98`，`app.js:264-272`）。

### 4.4 当前是否支持用户自定义每日能量

**不支持。** 全仓无 `dailyEnergy` / `manual` / `自定义能量` 相关实现。用户只能被动接受公式算出的 TDEE。

### 4.5 当前餐数是否存在、如何存储

**不存在。**

`DEFAULT_SETTINGS`（`app.js:52-60`）只有：

```js
mealSize, healthNutritionEnabled, members,
currentMealHouseholdSize, blockedKeywords, staple
```

⚠️ 注意命名易混：`mealSize` 是**每餐几道菜**（2/4/6/8），**不是每天几餐**。新增「每天几餐」时绝不能复用或覆盖它。

### 4.6 菜谱营养按什么范围计算

`estimateRecipe()`（`nutrition.js:179-212`）遍历 `recipe.ingredients` **全量相加**，即**菜谱原文所写用量的整份/整锅**，**未按人数折算**（数据里没有可靠的份数信息，`specs.md:133`、`README.md:247-252` 已如实声明）。

实测样本：`["昂刺鱼或者沙光鱼 一条", "豆腐 100 g", ...]`，部分条目带上游的 `* 份数` 标记，但没有可用数值。

### 4.7 主食量到底表示什么

- 存储：`settings.staple = { key, grams, auto }`；`auto` 时 `grams = 用餐人数 × 150g`（`app.js:390-393`）。
- 当前界面文案（`app.js:560-563`）：

> `全家的量，人均约 150 g（按 3 人自动）`

- **README 的表述（`README.md:161`）与硬约束 6/11 直接冲突**：

> 「**克数是「本餐全家实际吃掉的量」**，不是每个人的量。」

这是本轮**唯一一处文档与硬约束正面冲突**的地方，必须改写。

### 4.8 哪些 UI 文案会让用户把「每天」和「这一顿」混淆

| # | 位置 | 现文案 | 误导点 |
|---|---|---|---|

| D | `app.js:472` | 卡片 `约 xxx kcal` | 无范围限定；详情页有「（整锅）」而卡片没有，同一数字两种口径 |
| E | `app.js:612` | `菜谱未按人数折算，实际按你下锅的量同比变化` | 方向正确，但仍在「实际」口径里打转，没有点明「实际摄入本版本不知道」 |

## 8. localStorage 兼容 / 迁移方案

### 8.1 兼容策略：默认回填，不写迁移脚本

新增字段全部走「**读不到就用默认值**」，**不做一次性迁移写入**：

| 字段 | 老数据读取结果 | 回填值 |
|---|---|---|
| `settings.mealsPerDay` | `undefined` | `3` |
| `member.dailyEnergyMode` | `undefined` | `'auto'` |
| `member.dailyEnergyManual` | `undefined` | `null` |

理由：老用户在读取时得到「自动估算 + 每天 3 餐」，语义与老版本完全一致，无感升级。写迁移脚本反而会引入一次不可逆的本地数据改写。

### 8.2 ⚠️ 关键风险：`normalizeMember()` 的整条丢弃逻辑

`normalizeMember()`（`app.js:156-171`）最后一行：

```js
return validateMember(m) === null ? m : null;
```

**如果新增的能量校验写错，老成员会被整条丢弃**——用户升级后会发现成员全没了。

**实施时的硬性写法要求**：

```text
新增的能量校验必须放在 `if (m.dailyEnergyMode === 'manual')` 分支内。
auto 模式（含所有老数据）不得因为缺少 dailyEnergyManual 而被拒绝。
```

这条必须在实施阶段用「构造老版 members JSON → 读回」的断言验证，不能只靠人工检查。

### 8.3 既有迁移保持不变

`healthProfile → members`、`householdSize → currentMealHouseholdSize` 两条老迁移**原样保留**，不删不改。

### 8.4 回滚安全性

本轮新增字段为**纯增量**。若回滚到旧版本代码，旧 `normalizeMember()` 只挑它认识的字段，会**忽略**未知字段，不会崩溃，也不会丢数据（`mealsPerDay` 只是被忽略）。

## 10. 风险与回归点

| # | 风险 | 等级 | 缓解措施 | 回归点 |
|---|---|---|---|---|
| R1 | `validateMember()` 新增校验导致**老成员被整条丢弃** | 🔴 高 | 校验只放在 `manual` 分支内；用「老版 JSON → 读回」断言验证 | 老用户升级后成员列表 |
| R2 | 开关关闭时新增 UI（餐数设置、能量来源）仍在 DOM 中可见 | 🟠 中 | 餐数设置必须放进 `#hn-sections` **内部**，由既有 `renderHealthToggle()` 统一控制 | 关开关 → 首页与设置都应看不到营养内容 |
| R3 | 文案漏改，出现**新旧两套口径并存**（例：卡片说「整份」，详情说「整锅」） | 🟠 中 | 实施后全仓 grep 关键词清单：`维持能量`、`全家的量`、`人均`、`实际吃掉`、`本餐营养`、`整锅`、`每天` | 三处 kcal 展示（卡片/详情/面板）口径一致 |
| R4 | `mealsPerDay` 与既有 `mealSize` 命名混淆，误改每餐道数逻辑 | 🟠 中 | 变量名明确区分为 `mealsPerDay`（每天几餐）与 `mealSize`（每餐几道）；餐数**不参与任何计算** | 每餐 2/4/6/8 道菜功能不变 |

### 10.1 影响范围（blast radius）

本改动**触及共享计算与数据格式**（`validateMember` 被 `normalizeMember` 与表单保存两处共用），因此必须验证的 1–2 个关键事实：

1. **老数据（无新字段）经过 `normalizeMember()` 不被丢弃** ← 决定用户升级后数据是否还在
2. **关闭开关时不执行任何营养计算** ← 决定首页是否仍然极简

这两条无法从代码阅读「推断为真」，必须在实施阶段用**真实构造数据跑一遍**来证明。

### 10.2 局部与整体一致性（partial-vs-whole）

本轮改的是**一套跨界面的口径约定**（「这个数字是什么范围」）。因此除逐处改对外，还必须扫描同一约定下的**所有兄弟位置**：

- 卡片 kcal、详情页营养区、主食面板、这桌菜面板、成员健康参考卡、设置页边界说明、`README.md`、`specs.md`

任一位置仍停留在旧口径（如仍写「实际吃掉」），按**完整性发现**记录并报告，不静默扩大改动。
