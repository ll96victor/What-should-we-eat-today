## 6. §9.4 遗留技术决策的论证结论（规划 Agent 拍板，无需问用户）

### 6.1 白名单落地形态 = 独立文件 `data/meat-whitelist.json`（否决另外两案）

| 候选 | 结论 | 理由 |
|---|---|---|
| 构建脚本直接解析 `菜名清单-待勾选.md` | **否决** | ① md 是用户工作稿：勾选形态容错（x/X/√/删行/混用）成本高且永远堵不完，解析歧义 = 静默改池子，是最坏的失败形态；② 把「草稿」升格为「构建输入」后，用户任何误编辑（碰掉一行）都会改变全家菜单或直接弄坏构建；③ §8 已预警此路需重估位置与容错 |
| 并入 `data/dietary-rules.json` 一个字段 | **否决** | 忌口规则=安全底线（稳定、改错后果重：吃到不能吃的），白名单=口味偏好（常变、改错后果轻：吃到不想吃的）。**分文件 = 用户日后频繁增删爱吃的菜时，永远碰不到忌口规则文件**，把「非技术用户改坏安全规则」的概率降到零。两文件各自 fail-closed，成本相同 |
| 独立 `data/meat-whitelist.json` | **采纳** | 职责单一、改动隔离、各自 fail-closed、`_说明/_改法` 行内文档同样适用；md 清单保留为原始记录（证据链：用户勾选 → AI 转录 → 构建校验），日后争议可回溯 |

### 6.2 白名单与黑名单 = 两层都保留，不冗余

黑名单作用于**全库**（素菜池 39、非随机 6 类都不受白名单管，只有黑名单保护它们；朋友浏览详情页也看裁剪后数据——用户已确认全局生效）；白名单只作用于**荤菜随机池**。且黑名单校验白名单（§5.6-4、校验集 ⑤：白名单里出现被排除菜 → 构建失败），防「凭记忆把一道海鲜菜写进白名单」。两层是包含关系不是重复：白名单 ⊆ 黑名单过滤后的 protein 池。

### 6.3 NEW_DISH_ALERT 保留（轻量版），且新增「白名单存在性校验」

白名单模式下新上游荤菜不会自动进池（不在白名单），告警对荤菜的必要性确实下降；**但素菜池和非随机类对上游新菜仍然敞开**——新素菜只受词表保护，而「字面词表必然有漏网」是本项目实测过的教训（鱔 字案例，需求梳理 §6.4）。故保留轻量告警（基线对比 + 告警词命中 → 打印复核清单，不阻断），作为 `--refresh` 后的人工复核队列；specs/README 写明复核义务。上游改名场景由「恰好匹配/存在性」校验集兜住（强制排除、强制保留、白名单三张表全部失配即构建失败）。基线文件是**可再生派生缓存**（非 write-once 基线）：丢失只退化为「一次构建不告警 + 显式提示」，无静默风险。

### 6.4 `stats` 零变更（继承）

字段集合不动（不加 `stats.custom`/`stats.whitelist`）；数值随构建自动更新。计数口径用命令表达并写进 specs：如白名单道数 `node -e "const r=require('./data/recipes.json').recipes;console.log(r.filter(x=>x.menuRole==='protein').length)"`。

### 6.5 不新增独立「规则自检」命令（否决旧文档 §6 5.5 候选）

fail-closed 校验位于构建**最前段**（解析/联网之前），坏了立刻失败并给中文键路径错误——构建本身就是自检。独立命令 = 多一个要维护的入口 + README 多一节 + 用户多记一条命令，收益重复，违反设计原则 #1「不为未来可能的需求提前搭架构」。README 用户小节写明：「改完直接重跑构建；报错就按提示改，改不好找 AI」。

### 6.6 筛选逻辑正式化落点 = `build-recipes.mjs` 内部函数（不拆独立模块）

预计 +150 行（443 → 约 600 行），仍可控；拆 `tools/lib/dietary.mjs` 会引入项目 tools/ 目前不存在的目录层级与模块边界（现有 8 个脚本全部平铺单文件）。**「存疑区输出供人工复核」环节强制保留**（§6.4 教训的正式化：name/ingredients/description 命中 → 自动排除；仅 steps/tips 命中 → 保留 + 进复核清单；T1 对初始存疑清单逐条人工看，确有问题的报用户拍板，不得私自扩大排除表）。

## 8. 负向验证与回归清单（T8 全项，每条必须贴真实输出，断言非恒真自证）

**fail-closed 电池（规则文件）**——用临时副本目录或改后还原，每项验证后 `git status` 确认现场恢复：
1. 删除/改名 `dietary-rules.json` → 构建**失败**，中文报「文件缺失」（绝不是产出 370 道无忌口数据）
2. 破坏 JSON（去掉一个逗号）→ 失败，报「不是合法 JSON + 位置」
3. 删掉必需键（如 `排除食材.海鲜`）→ 失败，报具体键路径
4. `排除食材.海鲜` 置空数组 → 失败（核心词表不得为空）
5. 带 BOM 保存 → 构建**成功**（容错生效）
6. **非恒真自证**：以上任一失败场景修复后重跑必须成功——失败与成功输出都要贴

**校验集电池（三张表）**：
7. 强制排除表写一个不存在的菜名（如「温泉蛋蛋」）→ 失败并列出失配菜名
8. 强制保留表菜名改为不存在 → 失败
9. 白名单加入一道被排除的菜（如「水煮鱼」）→ 失败，错误信息说明「已被忌口规则排除」

## 11. 回滚

- 单 commit 交付：`git revert` 恢复代码+数据+文档；`history/` 另有 T2 文件级备份
- 分层回滚顺序：① 只想撤白名单 → `data/meat-whitelist.json` 改 `启用:false` 重建（回到 143 道忌口裁剪态）；② 想整体撤销 → `git revert` + 重跑两个构建 + 重新部署；③ 最后才考虑 history/ 手工恢复
