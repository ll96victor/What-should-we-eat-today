## 7. 为什么这样改

### 7.1 核心判断：计算层不动，只改语义层

`healthMetrics()` 的公式、`summarizeMeal()` 的算法、`estimateRecipe()` 的口径**一行未改**。

理由：用户要修的是「数字被理解成了错误的东西」，不是「数字算错了」。改公式会同时改变所有
已有数值，既无法回归对照，也不是本轮诉求。因此本轮只新增**派生函数**
（`dailyEnergyReference` / `macroRanges`），把「这个数字是什么范围、从哪来」显式表达出来。

### 7.2 一个必须修的显示缺陷

`.mf-field { display: flex; }` 会盖掉 `[hidden]` 自带的 `display: none`，
导致「自己设定」未选中时输入框**仍然可见**。这在真实浏览器里被实测抓到
（`hidden` 属性为 `true`，但 `offsetParent !== null`），已用 `.mf-field[hidden] { display: none; }` 修复并复测。

> 这正是自动化断言覆盖不到的部分：Node 侧断言只能验数据，DOM 可见性必须靠真实页面。

### 7.3 碳水/脂肪基准必须跟着每日能量走

原先碳水/脂肪由 `tdee` 推导。用户手动设 1800 后，若不改基准就会出现
「每日能量设 1800、碳水却按 2362 算」的新矛盾。所以抽出 `macroRanges(kcal)`，
以「每日能量参考」为唯一基准——**自动模式下它与旧算法数值完全一致**（有断言守护），
手动模式下才发生改变。

### 7.4 老数据一律默认回填，不写迁移脚本

新增字段全部走「读不到就用默认值」，不在 `localStorage` 里做一次性改写。
这样老用户在读取时直接得到「自动估算 + 每天 3 餐」，语义与升级前完全一致。
回滚到旧代码时，旧 `normalizeMember()` 会忽略未知字段，不会崩、不丢数据。
