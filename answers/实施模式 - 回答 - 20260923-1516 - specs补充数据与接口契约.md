## 4. 新增的 §6 内容结构

```text
6.1 本地存储        localStorage 键名、完整结构与默认值、成员对象字段、读取容错规则
6.2 recipes.json    顶层字段、单条菜谱 15 个字段、menuRole 8 个枚举与实际数量
6.3 foods.json      顶层字段、单条食物 6 个字段、主食标记、按个数换算的优先级
6.4 nutrition.js    别名索引 / 营养计算 / 健康参考 / 校验与常量 四组公开接口
6.5 界面常量        MENU_ROLES / MEAL_SIZES / PEOPLE / DEFAULT_DINERS / STAPLE_PER_PERSON / BLOCK_FIELDS
```

写这一节时坚持了一条边界：**只写跨实现必须一致的事实**（数据结构、字段名、枚举、函数输入输出），
**不写实现细节**（怎么渲染、怎么组织 DOM 属于实现自由）。
并在 §6.4 末尾显式声明 `fmt` / `coverageText` 这两个纯展示函数**不属于契约**。

## 5. 为什么这样改

### 5.1 实测证据（不是印象）

补充前逐个核对了 specs.md 是否覆盖重构必需的事实，结果：

| 关键契约 | 补充前 |
|---|---|
| `per100g` / `unitConversions` / `byUnit` / `perItem` | 全部未提及 |
| `ACTIVITY_LEVELS` 及四档系数（1.375 / 1.55） | 未提及 |
| `dailyEnergyMode` / `heightCm` 等真实字段名 | 未提及 |
| `estimateRecipe` / `summarizeMeal` / `healthMetrics` / `validateMember` 等函数 | 未提及 |
| `DIET_REFERENCE` | 未提及 |
| `menuRole` 完整枚举 | 只写了 protein / vegetable 两个 |

这些在 README 里也只有零散提及——但 README 是「对外说明书」，不该充当规格源。

### 5.2 顺带发现并更正的两处事实错误

1. **食物营养表条数**：文档写 120 条，`data/foods.json` 实际 **123 条**。
   查 git 历史确认该文件自提交起就是 123 条，**文档从一开始就写错了**，不是数据变化。
   specs.md 与 README.md 共 3 处一并更正。
   不修的话会出现「同一次改动里，新增的第 6 章写 123、第 9 章还写 120」的自相矛盾。
2. **标题与状态标记**：
   - 标题是「今晚吃什么」，而项目中文名已确认为**今天吃什么** → 改为今天吃什么，
     并在头部说明「代码与界面里显示的仍是旧名，这是尚未执行的重命名，不是两个项目」，
     避免重构者以为是两个项目。
   - 头部声明了 `⏳ 待用户真实验证` 这个标记，但**全文一次都没用过**。
     实际情况是：全项目**从未经过用户真实验收**。改为明确写出这一整体状态，
     说明 ✅ 只代表「实现完成且自动化验证通过」，不代表已被真实验收。

### 5.3 章节编号顺移

§6 插在「技术约束」之后、「设计原则」之前，原 §6–§10 顺移为 §7–§11。

## 8. 验证情况

### 8.1 契约真实性专项校验（本轮新增的验证）

合同文档写错比不写更糟，因此对 §6 写了**逐条对照校验**，
把 specs.md 里的声明与实际 `nutrition.js` / `data/*.json` / `app.js` 比对：

| 校验组 | 结果 |
|---|---|
| `nutrition.js` 全部 **28 个导出**（函数 + 常量） | ✅ 28 / 28 —— 要么有契约条目，要么显式声明豁免 |
| 常量取值（MAX_MEMBERS / NAME_MAX / 活动系数 / MEMBER_LIMITS / 状态文案 / 餐数选项） | ✅ 全部一致 |
| `recipes.json`：顶层字段、370 道、menuRole 8 个枚举及数量、单条 15 字段、difficulty 1–5 | ✅ 全部一致 |
| `foods.json`：123 条、staple 10 条、per100g 四键、unitConversions 双表 | ✅ 全部一致 |
| `app.js`：MENU_ROLES / MEAL_SIZES / PEOPLE / DEFAULT_DINERS / STAPLE_PER_PERSON / BLOCK_FIELDS / SETTINGS_KEY | ✅ 全部一致 |

**这次校验抓到了真实缺陷**：首次运行报 2 处失败，
排查确认**不是校验脚本写错，而是我的契约确实漏了**——
`normalizeMealsPerDay()` 是真实导出却未写入，`fmt()` / `coverageText()` 未做豁免声明。
补上后重跑 28 / 28 通过。这正是专项校验的价值。

## 10. 后续建议

1. **现在 specs.md 可以支撑重构了**，但建议重构时**先从 §6 抄契约，再照 §3 实现规则**，
   两者缺一不可。
2. 若近期要做微信小程序，`data/recipes.json` 与 `menuRole` 这套可直接复用，
   spec §6.2 已写明字段与枚举。
3. `<script type="module">` 与 ES Module 导入方式本身不是契约的一部分，
   小程序侧可自由替换为 CommonJS 或平台模块方案。
4. 项目名重命名（今晚吃什么 → 今天吃什么）仍**未执行**，涉及页面标题、页头、
   README 标题，需要时单独开一轮做纯文案统一。
