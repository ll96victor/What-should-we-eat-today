# 今天吃什么

一个纯静态的家庭小工具，只解决一件事：

> **每天做饭时，不知道今天吃什么。**

打开页面 → 自动给出荤素搭配的一桌菜 → 不满意就「换一组」→ 点菜名看完整做法。
目标是 10 秒内决定今天吃什么，不用注册、不用登录、不用联网调接口。

默认一荤一素，也可以在设置里改成 4 / 6 / 8 道（荤素始终 1:1），
或者把不想吃的食材（比如「鱼」「香菜」）加进屏蔽列表。

**首页默认只有菜。** 营养相关的功能（家庭成员、主食、本餐营养、健康参考）
都收在设置里的「健康与营养」开关后面，**默认关闭**；需要时打开即可。
营养数字全部来自本地数据，不联网、不调任何第三方接口。

## 快速开始

需要 Node.js（本机已验证 v24）。在项目目录执行：

```bash
node tools/serve.mjs
```

然后浏览器打开 <http://localhost:5173>。

> **不要直接双击 `index.html`。** 浏览器不允许 `file://` 页面读取本地 JSON，
> 直接打开会看到「需要通过本地服务器打开」的提示。用上面的命令起一个本地服务器即可。
>
> 不想用 Node 也可以：`python -m http.server 5173`，效果一样。

## 设置

入口在页面标题右上角的齿轮按钮。设置**存在浏览器本地**（`localStorage`，
键名 `what-should-we-eat-today.settings`），不上传、不需要账号，刷新和重开都还在。

保存的内容：`mealSize`（每餐道数）、`blockedKeywords`（屏蔽词）、
`healthNutritionEnabled`（健康与营养开关）、`members`（家庭成员，每人含自己的每日能量参考）、
`currentMealHouseholdSize`（本次用餐人数）、`mealsPerDay`（每天通常吃几餐）、
`staple`（主食种类与克数）。

> 换浏览器、换设备、或者清理浏览器数据后，设置不会跟过去——这是刻意的，本项目没有账户系统。

### 健康与营养（默认关闭）

设置里有一个总开关，**默认关闭**。关闭时：

- 首页只有菜、荤素角色、「换一组」和做法详情——**不显示任何热量或营养成分**
- 菜谱详情里没有营养区
- 主食、家庭成员、健康参考都不出现，也**不参与任何计算**

打开后才出现家庭成员、主食、本餐营养估算、健康参考。

关闭**不会删除**已填的数据：成员、主食设置、屏蔽词都留在浏览器里，重新打开开关就恢复。
随机菜单全程不受这个开关影响。

### 每餐菜品数量

可选 **2 / 4 / 6 / 8**，默认 2。荤素比例**始终 1:1**：

| 数量 | 组成 |
|---|---|
| 2 | 1 荤 + 1 素 |
| 4 | 2 荤 + 2 素 |
| 6 | 3 荤 + 3 素 |
| 8 | 4 荤 + 4 素 |

不会出现「4 道全是肉」这种情况。首页副标题会跟着数量变（「一荤一素」/「两荤两素」…），
不会和实际菜单打架。

### 屏蔽关键词

比如屏蔽「鱼」，那么 `清蒸鲈鱼`、`红烧鱼`、`鱼香肉丝` 都不会再被推荐。

- **匹配方式**：中文按「包含即命中」处理，不做分词
- **匹配字段**：菜名、分类名、简介、食材、标签（**不**匹配做法步骤和小贴士）
- **管理**：可以逐个添加、逐个删除，也支持一行输入多个（用逗号、顿号或空格分隔）；
  自动去掉前后空格、自动去重；也可以一键清空全部

> 屏蔽功能按菜谱文字做关键词匹配，只用来减少推荐；不能替代对实际食材和交叉接触风险的人工确认。

### 池子被屏蔽光了会怎样

不会死循环，也不会偷偷放宽你的屏蔽规则。页面会直接说明差在哪儿：

> 凑不出 8 道菜 —— 8 道需要 4 道荤菜 + 4 道素菜，但现在素菜只剩 2 道，需要 4 道。
> 减少几个屏蔽关键词，或者把每餐数量调小一点。

### 家庭成员

最多 **8 位**，点「＋ 添加成员」在弹出面板里填：称呼、性别、年龄、身高、体重、活动水平。

每位成员在列表里可以**编辑 / 停用 / 删除**。停用的人会置灰、保留资料但不计入默认用餐人数。
删除有一步确认（「删除『老婆』？」），不会动到其他成员。

> 成员资料**只保存在这台设备的浏览器里**，不上传、不跨设备同步、不需要账号。
> 换手机或清浏览器数据后需要重新填。

添加和编辑**共用同一个弹出面板**，没有两套表单。填得不合理会被拦下并说明原因
（称呼为空、年龄不在 10–100、身高不在 80–230、体重不在 25–200 等），不会存进去。
点「取消」不留下任何痕迹。

#### 每位成员自己的「每日能量参考」

**每人一份，彼此独立**——不会做成全家共用一个数字。同样是 30 岁的人，
健身教练和久坐上班族的参考值本来就不同。

每人可以各自选择来源：

| 来源 | 含义 |
|---|---|
| **自动估算** | 用这位成员自己的资料，按公开公式（Mifflin-St Jeor × 活动系数）算出来的粗略值 |
| **自己设定** | 你自己填的数字。程序**不判断它对不对**，填多少就按多少算 |

> **它是一整天的量，不是这一顿的量。** 指的是 24 小时内全部摄入（含早餐、午餐、晚餐
> 以及其他摄入）的参考值，**不是「你每天必须吃这么多」**，也不是用来算「这顿该吃多少」。

手动填的数字只做**技术防呆**（挡住多打一个 0、填成负数这类明显误输入），
**不是营养学标准，也不会拿它评价你设的值健不健康**。

### 每天通常吃几餐

可选 **2 / 3 / 4 / 5 / 6**，默认 3。

**这一项只用来记录你的饮食习惯，不参与任何计算。** 具体地说：

- 不会做「每日能量 ÷ 餐数 = 每餐应该吃多少」这种机械除法
- 不会把 2 餐写成 50/50、4 餐写成 25/25/25/25 之类没有依据的比例
- 不会因为这个设置改变首页的菜单、热量或任何营养数字

早餐也不在随机菜单的覆盖范围内：这个项目的菜单是家常正餐菜（一荤一素），
很多家庭的早餐并不是这个结构，所以**不会为了覆盖早餐而把早餐硬塞进菜单模型**。
「每天吃几餐」和「这桌菜是不是早餐」是两回事。

同理，「午餐 / 晚餐」在本项目里只是**食用时间标签**——中午炒一锅菜、晚上接着吃是
很正常的家庭场景，不存在「午餐必须一套新菜、晚餐必须再生成另一套」这种规则。

### 本次用餐人数

可选 **1 ～ 8**。这里和家庭成员**不是同一个数字**，也不会互相锁死：

| 情况 | 默认用餐人数 |
|---|---|
| 还没添加成员 | 你手动选的那个（默认 2） |
| 已添加成员 | **已启用成员的人数** |
| 已添加成员，但今天有人不在家 | 你可以临时改成实际人数，点「恢复为家庭成员数」可改回跟随 |

所以「家庭成员 5 人，今天实际吃 4 人」是完全合法的。

人数只影响**主食人均量、整顿饭总营养和人均营养**，不参与 BMI / BMR——
后者按每位成员各自的资料独立计算。

### 主食

菜单下方可以选主食（10 种：米饭、面条、馒头、面包、玉米、红薯、燕麦、小米、糙米饭、大米），
并填一个克数。

**克数是「本次用于计算的主食准备量」**——不是每个人实际吃了多少，
也不是「全家一定吃掉这么多」。

- 填 750g、5 人，界面会显示「人均 150g」。那只是把总克数除以人数得到的**数学平均**，
  不代表每个人都吃了 150g
- 默认按「用餐人数 × 150g」自动填，手动改过之后就不再自动覆盖
- 填 0 表示这顿不算主食

### 健康参考

**每位成员分别计算**，不把全家混成一个 BMI。每张卡片分两块，刻意不让它们混在一起：

**第一块：每日能量参考**（一整天 24 小时全部摄入的参考量，含早/午/晚及其他）

| 来源 | 依据 |
|---|---|
| 自动估算 | Mifflin-St Jeor 公式算 BMR，再乘活动系数（久坐 1.2 / 轻度 1.375 / 中等 1.55 / 高活动 1.725） |
| 自己设定 | 你自己填的数字，程序不判断对错 |

**第二块：体型与每天的宏量参考**

| 指标 | 公式 / 依据 |
|---|---|
| BMI | 体重(kg) ÷ 身高(m)²，分级按中国成年人参考标准 |
| 基础代谢 | Mifflin-St Jeor 公式（性别参与计算，男女相差 166 kcal）。**是静息状态下的估算，不是该吃多少** |
| 蛋白质 | 约 0.8 g/kg/天（按体重算，与能量来源无关） |
| 碳水 | **每日能量参考**的 45% – 65%（1g ≈ 4 kcal） |
| 脂肪 | **每日能量参考**的 20% – 35%（1g ≈ 9 kcal） |

碳水与脂肪是**占总能量的比例**，所以基准跟着上面那个「每日能量参考」走：
你把它设成 1800，这两个范围就按 1800 算，**不会出现「设了 1800、却按自动算出的 2300 算」**。

资料没填全的成员会标「资料不全」，不出结果也不猜。
这一节展示的是**参考范围**，不是「你必须吃多少」。

> BMI 是粗略筛查指标，不是医疗诊断。本节的数字仅供日常参考，不构成医疗建议、诊断或处方；
> 有疾病、孕期哺乳期或特殊饮食需求请咨询医生或注册营养师。

## 营养估算

> 整节功能都在「健康与营养」开关后面，**默认关闭**。下面的说明是打开后的行为。

### 先说清三个不是一回事的概念

界面上出现的数字只有前两类，第三类**本版本不知道，也不假装知道**：

| 概念 | 界面上的叫法 | 含义 |
|---|---|---|
| 每日能量参考 | 健康参考里的「每日能量参考」 | **一整天**（含早餐、午餐、晚餐及其他摄入）的参考量。**每名成员各一份**，来源可以是自动估算或自己设定 |
| 这桌菜估算 | 首页的「这桌菜估算」 | 按**菜谱所写用量** + 本次填的**主食准备量**算出来的估算。「÷ 人数」得到的人均只是数学平均 |
| 实际摄入 | 不出现 | 这一顿实际吃进去多少，**当前版本算不出来**，也不会拿别的数字顶替 |

同样重要的一条边界：

> **菜谱用量 ≠ 你实际买的量 ≠ 你实际下锅的量 ≠ 你实际吃进去的量。**
> 菜谱写牛肉 200 g，你可能买了 300 g，也可能只用了其中一部分。
> 所以界面上的数字一律写成「按菜谱用量估算」——那是唯一有依据的口径。

### 数字从哪来

营养数值全部来自 **[USDA FoodData Central](https://fdc.nal.usda.gov/)**，
授权为 **CC0 1.0（公有领域贡献）**，可自由再分发。使用的是 SR Legacy（2018-04）与
Foundation Foods（2026-04-30）两个数据集。

**运行时完全不联网**：构建时下载 → 筛选出用到的 123 种食物 → 固化成本地
`data/foods.json`（25 KB）。页面只读这份文件，不调用任何第三方接口（包括 USDA 自己的 API），
所以国内网络直接可用。

> **为什么不用《中国食物成分表》**：该书是正式出版物，存在版权限制；
> 网上流传的衍生数据集（如 GitHub 上的 OCR 版本）经核查**没有 LICENSE 声明**，
> 不可重新分发。因此营养数值一律采用版权明确的公有领域数据。

### 怎么算

```text
菜谱食材文本
  → 认出是哪种食物（最长别名优先，避免「老豆腐」被「豆腐」抢先匹配）
  → 解析出克数（明确重量优先；否则按「个数 × 单重」折算）
  → 乘食物营养表
  → 整道菜相加
本餐合计 = 各道菜 + 主食
人均    = 本餐合计 ÷ 用餐人数
```

数值**不是手抄的**。`tools/build-foods.mjs` 里只维护「中文食材名 → USDA 记录编号」的对照关系，
每个数字都由脚本从 USDA 原始数据按键取出，因此不会出现录入笔误，也能逐条回溯。

### 覆盖率和它的诚实边界

这份数据里不是每道菜都能算清楚。界面会如实标出三种状态：

| 状态 | 含义 |
|---|---|
| **已估算** | 这道菜所有食材都认出来了 |
| **部分估算** | 只算出了其中一部分，卡片上的热量带 `*` 号 |
| **暂无完整估算** | 一个食材都没认出来，此时**不给任何数字**，只说明原因 |

当前的实际情况（370 道全量统计，可用 `node tools/check-nutrition.mjs` 复现）：

> 口径层面另有一个自检：`node tools/check-nutrition-semantics.mjs`。
> 它不检查估算准不准，而是检查**语义有没有跑偏**——每日能量 / 这桌菜 / 实际摄入
> 三个概念有没有被混着用、手动设定的能量有没有被自动值顶掉、
> 老版本存的成员会不会被新校验误杀。改营养相关代码后建议一起跑。

| 状态 | 道数 | 占比 |
|---|---:|---:|
| 已估算 | 121 | 32.7% |
| 部分估算 | 234 | 63.2% |
| 暂无完整估算 | 15 | 4.1% |

食材级别的识别率是 **80.8%**。认不出来的主要原因是上游菜谱里写了
「豆瓣酱」「花椒」「味精」这类食物（食物表里没有），或者只写「适量」「少许」没有数字——
**这些一律不猜重量**，宁可少算也不虚构。

为保证不给出明显离谱的数字，做了两条额外处理：

1. **油炸用油不计入**。像「熟猪油 2000 克」这种是一整锅炸油，不可能被吃掉，
   全额计入会算出「一道菜两万大卡」。超过 150g 的用油判为炸油，不计入，并在界面上说明。
2. **说明文字不算食材**。上游数据里混着少量解释性文字（例如「水的体积是米饭的体积的 9-12 倍。」），
   它们不是食材，既不参与计算，也不算进覆盖率分母。

### 一处未实现的折算

**菜谱营养按菜谱原文所写的用量（整份）计算，没有按人数折算。**
因为上游数据里没有可靠的「几人份」信息，凭空推断会得到假精确的数字。

所以界面上：

- **这桌菜估算** = 各道菜的整份估算 + 本次填的主食准备量
- **人均** = 合计 ÷ 用餐人数，**只是一个数学平均值**
- 它不代表每个人实际吃了相同份量，也不代表你买了、用了菜谱写的那点食材

界面上对这一点有明确说明，不靠用户自己去猜。

## 菜谱数据

### 来源

菜谱来自开源项目 **[Anduin2017/HowToCook](https://github.com/Anduin2017/HowToCook)（程序员做饭指南）**，
上游采用 **Unlicense**（公有领域）授权，可自由使用与再分发。

本项目**只提取 V1 真正需要的文字信息**（菜名、食材用量、做法步骤、小贴士、来源链接），
不复制上游项目结构，也不下载上游图片。

当前收录 **370 道**（上游 371 篇，其中 1 篇同名重复已合并）：

| menuRole | 数量 | 说明 |
|---|---:|---|
| `protein` | 188 | **随机池**：肉、水产、蛋、豆腐、豆类，含肉汤 |
| `vegetable` | 40 | **随机池**：以蔬菜为主料的家常素菜 |
| `staple` | 75 | 主食、粥、面点（不进随机池） |
| `dessert` | 26 | 甜品、糖水（不进随机池） |
| `drink` | 23 | 饮品（不进随机池） |
| `condiment` | 10 | 调料酱汁（不进随机池） |
| `breakfast` | 7 | 佐餐小食：水煮蛋、卤蛋等（不进随机池） |
| `other` | 1 | 烹调技法演示，不是一道具体的菜（不进随机池） |

随机池共 **228 道**（188 × 40 = 7520 种搭配组合）。

三类条目被有意**不放进随机池**（数据完整保留，以后做搜索或浏览时可直接用）：

- **佐餐小食**：白煮蛋、温泉蛋、卤蛋等。它们确实提供蛋白质，
  但抽到「溏心蛋 + 蒜蓉西兰花」不像一顿正经晚饭。
- **甜品当素菜**：拔丝土豆主料是 120g 白砂糖裹土豆，放进「今天的素菜」会让人费解。
- **技法演示**：水油焖蔬菜的食材只写「叶菜类蔬菜 300~500g」，是一套做法而不是一道菜。

### 已知局限：蔬菜池只有 40 道

这是当前 V1 最明显的一处不足，如实记录：

| 使用强度 | 遇到重复素菜的概率 |
|---|---|
| 一次会话（连点 5 次换一组） | 约 23% |
| 连用一周（每天 3 次，共 21 次） | 约 99.8% |

对比之下，如果蔬菜池有 1000 道，这两个数字分别是 1% 和 19%。

**为什么不直接补数据**：需求目标是 1000～3000 道，但经过实际检索，
**没有找到第二个「授权清晰 + 含做法步骤 + 可自动整理」的中文菜谱来源**：

| 候选 | 结论 |
|---|---|
| `Anduin2017/HowToCook` | ✅ 已采用。Unlicense，371 篇，含完整做法步骤 |
| `liu-ziting/what-to-eat`（3542★） | ❌ **无 LICENSE**，不可合法复用 |
| `Decade-qiu/CookHero`（Apache-2.0） | ❌ 是基于 LLM 的应用，没有静态菜谱数据集 |
| `zjc17/cook.zhangjc.tech`（GPL-3.0） | ❌ 有 606 条数据，但**只有菜名+食材+视频链接，没有做法步骤**；且 GPL 传染性 |
| `huggypig/HowToCookVegan` | ❌ 仅 17★、133 文件、授权 NOASSERTION，不构成可靠来源 |

在找到可靠来源之前，宁可保持 40 道真实数据，也不引入版权不清或质量不可控的内容。

**关于数量**：需求目标是 1000～3000 道。上游 HowToCook 公开的高质量中文菜谱总量就是 371 篇，
本项目没有为了凑数去抓取版权和质量无法确认的数据源。缺口的补齐方式见文末「下一步」。

### 字段说明

```jsonc
{
  "id": "htc-1a2b3c4d5e",     // 稳定 id，由上游文件路径派生
  "name": "西红柿炒鸡蛋",
  "menuRole": "protein",       // ★ 随机菜单归属：protein | vegetable | staple | ...
  "category": "vegetable_dish",// 上游原始分类，保留用于展示与以后扩展
  "categoryName": "素菜",       // 分类中文名
  "description": "一道酸甜开胃的家常菜肴……",
  "ingredients": ["西红柿 = 1 个（约 180g） * 份数", "..."],
  "steps": ["西红柿洗净", "..."],
  "tips": ["快速做法：……"],
  "difficulty": 2,             // 1~5 星，可能为 null
  "calories": null,
  "imageUrl": null,            // 预留字段，V1 不使用（见下）
  "sourceName": "HowToCook 程序员做饭指南",
  "sourceUrl": "https://github.com/Anduin2017/HowToCook/blob/master/...",
  "referenceName": "...",      // 上游标注的参考视频/文章，可能为 null
  "referenceUrl": null,
  "tags": ["素菜", "新手友好"]
}
```

**`menuRole` 是最重要的字段**，决定这道菜进哪个随机池。上游按「荤菜 / 素菜」分目录，
但家常菜里鸡蛋、豆腐、豆类同属蛋白质来源，部分肉汤也实际是正经菜，因此生成脚本里有一张
**人工复核的修正表**（`tools/build-recipes.mjs` 的 `ROLE_OVERRIDE`），逐条把语义纠正到位。

### 图片

`imageUrl` 字段保留但当前**全部为 `null`**。原因是上游图片托管在境外 CDN，
而本项目面向国内家庭网络，不适合把图片作为核心依赖。

**没有图片不影响任何功能**：卡片用类别配色 + emoji 兜底，详情页完全是文字。
以后接入国内可访问的图床时，只要往 `imageUrl` 填地址即可自动生效，
图片加载失败也会自动回落到 emoji（`app.js` 的 `cardVisual()`）。

### 重建数据

```bash
node tools/build-recipes.mjs            # 用本地缓存重建
node tools/build-recipes.mjs --refresh  # 强制重新联网拉取上游最新菜谱
```

上游 md 原文缓存在 `tools/.cache/`（不入库）。重建后会打印数据校验结果。

### 腾讯云 CloudBase 静态托管

同样是把仓库根目录作为站点根目录，不需要数据库、云函数或任何后端资源。

**方式一：控制台手动上传（最省事）**

tcb login                                          # 首次需要登录

`answers/` 等与站点无关的内容），再执行 `tcb hosting deploy dist / -e <环境ID>`。
如果暂时不传环境 ID，它只准备 `dist/` 目录并提示后续命令。

## V1 范围

- 打开页面自动给出 **荤素 1:1 的一桌菜**（默认 1 荤 1 素）
